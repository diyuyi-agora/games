# 打击感优化调研：从“更强”到“更清楚”

调研日期：2026-10-30。本文把公开资料中的观点转换成可落地的优化顺序，并标出哪些内容是资料原意、哪些是针对本 Demo 的设计推导。外部资料未被当作本项目参数的直接依据。本文是研究和后续实现方案；本轮保留游戏实现不变。

## 1. 先定义要优化的结果

“打击感”不是单一的震屏强度。建议把体验拆成四个可观察结果：

| 结果 | 玩家应该能回答的问题 | 优先测试的指标 |
| --- | --- | --- |
| 操作归因 | 这是我发起的动作吗？ | 输入到起手的延迟、丢输入率 |
| 接触确认 | 我真的打中了吗？ | 命中辨识正确率、接触点时序 |
| 力量传递 | 目标承受了什么？ | 目标反应方向、位移、硬直和材质一致性 |
| 战斗可读性 | 这次反馈是否帮助下一步判断？ | 预警识别率、反击成功率、误操作率 |

因此，“更爽”不应作为唯一验收标准。一次反馈如果更强烈，却遮住了敌人的预警或让输入变慢，战斗质量可能下降。

## 2. 公开资料带来的六条原则

### 原则 A：先调控制，再调装饰

Steve Swink 的 *Game Feel* 的出版社页面提供了以虚拟感受和控制为核心的阅读入口。本项目沿这一方向提出实用顺序：先确保输入响应和动作状态可信，再用停顿、声音、粒子和镜头放大已经成立的因果关系。这个优先级是本项目的建议，并非出版社页面给出的实验结论。

**对本 Demo 的推导：**先关闭所有反馈，确认挥空、命中、击退、受击硬直和连击缓存仍然可判断；然后每次只打开一个反馈通道。这样不会把“判定错误”误诊为“特效不够强”。

### 原则 B：反馈需要有重音、层级和留白

Jan Willem Nijman 的 *The Art of Screenshake* 与 Martin Jonasson、Petri Purho 的 *Juice it or lose it* 是本主题的经典观看入口，本轮核验了标题和简介。本项目从反馈组合这一方向提出假设：反馈强度应该跟事件重要性相关，并且需要对比度；持续使用高强度会降低关键事件的辨识度。这需要通过连续体验来验证。

**对本 Demo 的推导：**轻击一式、二式、三式和重击使用递增的停顿、击退与特效；装甲承受使用不同于破甲的声音和位移；试炼预警保留视觉空间，不让命中特效覆盖敌人动作。

### 原则 C：接触瞬间要由多个通道同时确认

命中动画、声音、特效、镜头和目标反应不必同样强，但应该在相同的时间窗口表达同一件事。尤其要保证接触点与目标位移前的位置一致。否则玩家看到的“闪光”可能落在敌人已经被击退后的地方，反馈会像延迟或穿模。

**待实现优化：**当前 Demo 先立即修改目标位置，再从新位置生成碎屑和冲击环。建议在击退前捕获接触点，用它生成接触特效；刀光继续沿武器轨迹绘制。这样可把接触火花与击退后的跟随效果区分开。

### 原则 D：镜头运动应该是可控的动态系统

Ryan Juckett 的 *Damped Springs* 说明，弹簧和阻尼可以让镜头在冲击后平滑回位，避免瞬间跳到新位置；同时强调运动要与时间步长无关。Gaffer On Games 的 *Fix Your Timestep!* 则说明，直接把可变帧时长送进模拟会造成帧率相关的行为，影响物理、碰撞和手感。

**对本 Demo 的推导：**镜头震动应拆成“冲击输入、方向、频率、阻尼”四个参数，而不是简单随机抖动。下一步可将当前的衰减位移升级为阻尼弹簧，并把战斗状态更新改为固定或半固定时间步；渲染再插值。这样不同刷新率下，停顿、击退和闪避窗口更稳定。

### 原则 E：音频要按重要性混音

GDC Vault 对 *The Audio Technology of Torchlight 3* 的介绍提到，动作 RPG 需要处理大量敌人、技能、宠物、玩家和环境声音，相关方案包括 importance-based mixing、volumetric sounds 和 screen-space distance attenuation。

**对本 Demo 的推导：**命中声应该有优先级和限流策略：玩家自己的关键命中最高，普通敌人命中按距离衰减，连续粒子或多目标事件共享一个短时预算。后续可加入同类声音的 voice stealing、材质总线和重击 ducking，避免“声音越多越糊”。

### 原则 F：强反馈必须有可访问的替代方案

Microsoft 的 Xbox Accessibility Guideline 117 建议为镜头移动、震屏、运动模糊、FOV 等提供关闭或强度调节，原因包括晕动症、注意力和阅读障碍。它还举例说明 Halo Infinite 提供径向模糊、屏幕震动、全屏效果和速度线的独立强度控制。

**对本 Demo 的推导：**震屏、命中特效和音效应保持独立开关；“减少动态效果”应至少关闭镜头震动；如果扩展到 3D，应加入 FOV、镜头距离和自动回中设置。强反馈的可访问性不是削弱设计，而是让玩家可以保留自己能承受的反馈通道。

## 3. 推荐的优化顺序

按风险和收益排序，而不是按“看起来最炫”排序：

1. **时序校准。**用帧步或录制回放检查输入、动画接触、判定、VFX 和音频是否在同一时间窗。先修正提前／滞后，再调参数。
2. **判定与表现分离。**攻击碰撞、受击硬直和击退属于战斗规则；停顿、闪白、震屏、粒子和声音属于表现层。这样可以比较反馈而不偷偷改变玩法。
3. **攻击层级。**为轻击、重击、破防、终结分别设定接触时长、位移、声音频段和视觉面积，避免所有攻击使用一个“命中模板”。
4. **目标反应。**先定义方向、材质和状态，再制作动画。霸体、格挡、装甲承受和普通受击要有可辨识的反馈。
5. **镜头阻尼。**把冲击镜头改为方向性脉冲＋阻尼回位；限制峰值和累计，避免连续小命中把镜头抖成噪声。
6. **混音预算。**对关键命中、敌方预警、受伤和环境建立优先级；限制同一时刻活跃的短音效数量。
7. **强度和无障碍。**开放每个主要通道的独立强度，加入低动态预设，并在手机、低帧率和大屏距离下复测。

## 4. 建议的参数化方式

不要把反馈写成一堆分散的常数。每个攻击可以使用一个数据对象：

```js
{
  id: 'heavy',
  phase: { anticipation: 280, active: 70, recovery: 440 },
  hit: { damage: 42, range: 221, knockback: 71, stun: 730 },
  feedback: {
    hitStop: 110,
    shake: { amplitude: 12, frequency: 22, damping: 8 },
    audio: { bus: 'playerHeavy', priority: 1.0 },
    particles: { count: 26, radius: 110 }
  }
}
```

这样可以把“动作慢但命中重”和“动作快但接触锐利”作为不同的可测试配置。反馈强度应在表现层乘算；伤害、范围、击退和硬直除非明确要做平衡实验，不应被同一个强度滑条改写。

## 5. 建议的测试协议

### 单变量 A/B

固定角色、目标、站位、音量、刷新率和攻击序列。A、B 的玩法规则完全一致，只改变一个反馈通道。每位体验者交替体验顺序，避免先体验的版本获得熟悉度优势。

每次命中后让体验者分别评分：

- 命中是否清楚（1～7）；
- 力量是否可信（1～7）；
- 是否能立刻准备下一步（1～7）；
- 是否感到过度刺激（1～7）。

### 任务指标

- **命中辨识率：**随机出现命中、挥空、格挡、装甲承受，记录判断正确率。
- **反击成功率：**有预警的敌方攻击中，记录玩家是否在窗口内闪避或打断。
- **输入丢失率：**在起手、命中停顿、受击硬直附近连续输入，统计没有进入缓存／队列的次数。
- **完成时间与错误：**完成固定连段和试炼的时间、误攻击、误闪避、被打断次数。
- **疲劳与偏好：**连续体验 5～10 分钟后再问强度偏好；短时“更爽”不一定等于长时“更好”。

### 录制与回放

将每次攻击记录为：输入时间、动画相位、碰撞时间、反馈开始时间、目标反应开始时间和音频播放时间。回放时可对比不同预设，避免依靠记忆评价。浏览器音频还存在输出延迟；如果需要精确校准，可用 Web Audio 的 `AudioContext.getOutputTimestamp()` 对照音频输出时间。

## 7. 现有 Demo 的具体诊断

以下定位对应调研时的 `game.js`，后续修改后行号可能变化。

| 问题 | 代码证据 | 体验风险与建议 |
| --- | --- | --- |
| 火花产生在位移后的位置 | 第 146 行更新 `enemy.x`，第 153 行才生成接触坐标 | 标准重击在未被边界裁剪时移动 71 单位，特效原点随之平移。优先保留位移前接触点；击退可另用短动画表现 |
| 判定范围与实体刀刃分开定义 | 攻击范围为 179～221，刀尖局部长度 118，手部水平偏移约 17～18，刀光又使用独立椭圆 | 关闭刀光后可能出现实体刀刃未接触而扣血。需先决定范围代表实体剑刃还是剑气，再用可视化判定检查；不要直接把所有宽容判定都删除 |
| 单个时刻判定 | 第 253 行跨过 `contact` 时只调用一次 `impact()` | 这是单次采样，不是完整的有效帧范围。高速移动和帧率波动下可能出现视觉穿过而未命中；候选方案是有效窗口内扫掠碰撞，并对每个目标去重 |
| 混合计时规则 | `chainAge` 在停顿前增长；缓存寿命、无敌、敌人硬直在停顿后更新 | 命中停顿占用连段时间，却延长缓存和无敌的真实持续时间。先写清现实时间、战斗时间、表现时间分别控制什么，再统一实现 |
| 输入仅保留一个槽 | `queued = { kind, life: .24 }` 覆盖前一条输入，过期后删除 | 重击早期的预输入可能在动作结束前失效，后按键会覆盖前按键。需要定义缓存接受阶段、覆盖优先级和取消窗口，再测丢输入率 |
| 闪避尚无攻击取消窗口 | 有攻击时先入缓存；只有 `!attack` 才消费缓存 | 攻击期间按闪避并不会立刻闪避。是否增加命中后取消、后摇末段取消，应作为战斗规则实验，与表现强度实验分开 |
| 面板显示配置值 | 第 162 行直接输出 `freeze`，不是测量冻结的实际时长 | “110 ms”不能当作实测。应分别记录请求停顿、实际恢复时间和额外帧延迟 |
| 低帧率时丢弃经过时间 | `frame()` 把 `dt` 截到 35 ms，并无累加器补回差值 | 模拟含倒计时都会变慢；需明确是否暂停／补步，并把真实时间试炼与动画模拟区分 |
| 震动频率过高且不按出手方向变化 | 位移使用 `sin(time*171)`、`cos(time*139)`，与攻击方向无关 | 约 27.2 Hz 和 22.1 Hz，在 30 fps 下可能混叠。先试较低频、按冲量方向回弹，再比较可读性与疲劳 |
| 音色依赖目标身份而非当前装甲状态 | `sound()` 使用 `enemy.armored`，破甲没有改变该标记 | 若破甲后希望材质变化，应传入 `armorActive`／材质事件；若机体一直为金属则可保留。需要先明确材质语义 |

### 停顿与帧率的计算例子

当前逻辑每次进入 `freeze > 0` 分支，就减去一个完整 `dt` 并跳过该帧战斗更新。以稳定帧时长、完整冻结区间估算，耗时约为 `ceil(请求时长 / dt) × dt`：

| 请求停顿 | 30 fps | 60 fps | 144 fps |
| --- | ---: | ---: | ---: |
| 45 ms | 66.7 ms | 50.0 ms | 48.6 ms |
| 110 ms | 133.3 ms | 116.7 ms | 111.1 ms |

这是对离散更新的数学估算，不是实际设备测量；帧抖动、命中相位和输出链路还会增加误差。固定步长能稳定战斗模拟，但可见停顿仍受到显示刷新率限制，不能宣称消除所有输入或显示延迟。

同样，在稳定 20 fps、没有后台暂停的理想例子中，每帧实际经过 50 ms，却只累计 35 ms，原型里的“30 秒”约需 `30 / (20 × 0.035) = 42.9` 秒现实时间。这说明性能和打击节奏必须一起设计。

## 8. 建议先做的五组实验

以下是围绕现有参数给出的测试水平，不是业界标准或已验证的最优值。

| 实验 | 固定条件 | 改变什么 | 重点判断 |
| --- | --- | --- | --- |
| 重击停顿 | 伤害 42、相同动作与站位 | 50 / 80 / 110 ms；先验证实际时长 | 哪个水平足够明确，哪个开始拖慢下一步 |
| 接触点 | 同一攻击和相同粒子数量 | 位移前原点 / 位移后原点 | 接触是否准确，是否像“隔空击中” |
| 输入缓存 | 相同攻击数据、停顿和取消规则 | 120 / 180 / 240 ms | 预输入成功率、误触发、是否有失控感 |
| 镜头 | 同一冲量幅度、关闭自动缩放 | 当前高频位移 / 低频阻尼回弹 / 无震动 | 清晰度、预警辨识、连续体验不适 |
| 音效 | 相同响度和命中次数 | 单音层 / 接触瞬态＋主体＋尾音 | 材质辨识和力度是否提升，而非只是更响 |

每个实验先做两个水平的比较；表中三个数值是候选水平。体验者较少时先找明显问题，再用更多人和反向顺序复核，不将小样本偏好外推为普遍结论。

### 武器与材质的扩展矩阵

| 类别 | 优先表达 | 不宜默认依赖的手段 |
| --- | --- | --- |
| 短刀／高频连击 | 快速接触确认、小幅局部反应、短促清晰声 | 每次长时间全局停顿与大幅震屏 |
| 大剑／锤击 | 身体驱动、释放加速、接触阻力、失衡和余势 | 全程等比例减速 |
| 金属装甲 | 高频接触、短共鸣、局部火花、承受与破甲区分 | 只降血却没有承受表现 |
| 肉体 | 局部形变、受击方向、较短低中频主体声 | 直接复用金属共鸣 |
| 石体 | 裂缝、碎片、结构性破坏、不同阶段音色 | 每一击都同样大小的碎裂爆发 |
| 护盾 | 清晰格挡边界、反作用、盾面波动与破盾事件 | 与普通命中相同的颜色、声音和状态 |

以上为原型设计建议，并非这些类别必须使用的唯一表现。

## 10. 实施建议

建议把一次命中当成需要同步表达的事件：玩家输入有响应，攻击有蓄势和释放，碰撞在正确位置发生，目标以符合材质和规则的方式回应，声音和镜头帮助玩家判断下一步。先完成计时记录和接触点校准，再分别验证输入缓存、命中停顿、阻尼镜头与混音，最后扩展武器和材质。每一轮用固定任务和单变量比较决定是否保留改动。
